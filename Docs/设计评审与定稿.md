# 《女娲补天》设计评审与定稿记录

> 评审对象：《女娲补天 · 对话交接文档（定稿版）》
> 评审日期：2026-10-19
> 用途：实现阶段对照清单。每条结论给出「问题 → 后果 → 定稿修法」，编码时逐条落实。

## 总体结论

设计整体**可行**：状态机闭环（LingShiState / GameState / grid -1/0/1/2）、决策有理由记录、实现分六阶段且各有验证点、核心逻辑（ShapeCutter / MatchChecker / Hole / LingShiShape）刻意做成纯 C# 类便于测试——这些继续保持。

评审发现 **6 个照原文档伪代码实现必炸的问题**（其中 2 个死局级）+ 一批由「Steam / TapTap / 微信·抖音小游戏多平台发布」目标触发的设计缺口。以下为逐项定稿。

## 一、P0 阻断级问题与定稿修法

### P0-1 洞合并导致单关永远无法胜利（死局）—— 定案：保留合并 + 配额回退

- **问题**：胜利条件 `filledHoleCount == totalHoles`（每闭合一个洞 +1），但 2.7 允许新洞与已有未填洞合并，合并后两个洞变一个，实际可闭合洞数 = totalHoles − 合并次数，永远到不了 totalHoles。
- **定稿修法（配额回退法）**：合并提交时 `generatedHoleCount--`（被吞洞返还配额）。数学上每次生成 +1、每次合并 −1，最终实际可闭合洞数恒等于 totalHoles，胜利条件与 UI 显示 X/totalHoles 均不用改。副作用：合并过的关卡会多生成几批洞，语义合理。
- **连带的蔓延规则修订（必须一起改，替换原文档 2.7 节）**：

```text
蔓延规则（修订版）：
1. CanSpread：蔓延只能进入 grid == -1 的格子，
   且该格不得与「已填过的洞」（nowCellCount > 0）的任何格子相邻
   —— 已填洞周围永远保持 ≥1 格安全距离，"连体不合并"问题从源头消失。
2. 本洞生成时 roll 一次 mergeChance：
   - roll 通过 → 本次蔓延允许贴向「未填洞」（nowCellCount == 0）的格子
   - roll 未通过 → 蔓延同样禁止贴向任何已有洞
3. 蔓延结束后若与未填洞相邻 → 必然合并（贴上了就必须合，
   不允许"贴着却不合并"出现在场上）；
   若合并后总格数 > maxMergedHoleSize，则该新洞生成作废，重选种子重试。
4. 合并提交时：generatedHoleCount--（配额回退）。
```

> 关键变化：mergeChance 语义从「合并概率」改为「允许贴向未填洞的概率」，且**相邻即必合**。场上永远不存在两个贴着却互不相容的洞。

### P0-2 OnMouseDown 时序 bug：拾取暂存块会把自己"回收"进背篓

- **问题**：伪代码顺序 `TryPickUp → ReturnStashedToBasket() → StartDrag(ls)`。若点起的正是暂存列表里那块半透明 Cooked 灵石（collider 未禁用，可被拾取），它会先被 `ReturnStashedToBasket` 送回背篓，又被 `StartDrag` 拖起 → 同一块同时在背篓列表和拖拽中，重复添加、计数错乱、ClearAll 时序撞车。
- **定稿修法**：`ReturnStashedToBasket(except: ls)` —— 拾取的若是暂存块，只从暂存列表移除它，其余暂存块照常回收。

### P0-3 InBasket 灵石误入暂存 → 跳过熬煮，核心玩法崩坏

- **问题**：`OnMouseUp` 失败路径无条件进 `stashedLingShi`，而暂存语义是"保持 Cooked"。InBasket 灵石若进暂存，下次回收走 `AddCookedLingShi`，未熬煮的石头会变成 Cooked 直接上工作台。
- **定稿修法**：**暂存列表只接受 Cooked 状态；InBasket 拖放失败一律物理回背篓**。`AddCookedLingShi` 内部加 `Debug.Assert(ls.GetState() == LingShiState.Cooked)` 防御。

### P0-4 OnMouseUp 缺「锅 / 背篓」判定分支

- **问题**：2.1 规则表定义了"InBasket 拖到锅 ✅""Cooked 放回背篓 ✅"，但伪代码只有"网格匹配成功 / 失败进暂存"两条路，`IsPointerOverPot()` 无调用点。
- **定稿修法**：用以下优先级伪代码替换现有 OnMouseUp 判定：

```text
OnMouseUp(screenPos):
  ls = draggingLingShi
  ① 指针在锅区 && ls.state == InBasket:
       potManager.TryAddLingShi(ls) 成功 → 进锅开始熬煮
       失败（锅满）→ 物理回背篓（给提示音/抖动反馈）
  ② else if ls.state == Cooked && MatchChecker.CanPlace(...) 成功:
       TryPlace() 吸附放置
  ③ else if 指针在背篓区:
       回背篓（InBasket 直接落入；Cooked 走 AddCookedLingShi 保持状态）
  ④ else:  // 野外松手
       Cooked → 进暂存（半透明悬空）
       InBasket → 物理回背篓
```

- 顺带：2.11「从已放置取下先缩到 0.6 再到 1.0」多此一举，直接过渡到 1.0。

### P0-5 灵气消耗公式语义歧义 —— 定案：只扣 grid==0

- **问题**：原文「消耗 = 当前所有未填洞的格子总数 × qi/s」有歧义：含不含已被灵石盖住的格子？
- **定稿**：**只扣 grid==0 的空缺格**（已填格、闭合中 grid==2 一律不扣）。理由：符合"堵住就不漏气"的直觉，每次放置立刻有正反馈（灵气掉速肉眼可见变慢）。
- 配套：`GetUnfilledCellCount()` 只统计 grid==0；建议维护缓存计数（放置/取下/闭合时增减），不要每帧遍历求和。

### P0-6 跨洞挪用灵石被销毁 → 原洞永久无解（死局）—— 定案：绑定来源洞

- **问题**：ShapeCutter 只保证"切出的灵石能拼满本洞"，没规定灵石只能放回本洞。洞1的必需块形状恰好匹配洞2 → 放进洞2 → 洞2闭合销毁该块 → 洞1 永远缺一块，无任何机制保证可拼满 → 玩家耗死。低概率但故意操作必现。
- **定稿修法**：灵石记录 `sourceHoleId`，MatchChecker 增加校验——必需灵石只允许放回来源洞；冗余灵石 `sourceHoleId = null` 放行任意洞（冗余块不属于任何必需集，销毁无影响）。
- **配套 UX（必须做，否则限制感很强）**：预览高亮区分两种无效——「形状不匹配」和「形状匹配但非来源洞」用两种不同颜色/标记。
- **待办**（见第六节）：发布前评估放宽绑定 + 死局检测，给玩家更多自由。

## 二、跨平台决策（已拍板定稿）

目标平台：Steam（PC）+ TapTap（移动）+ 微信/抖音小游戏。完全免费无广告。

### 2.1 旋转输入：屏幕按钮默认 + 双指扭转可选

- **定稿**：阶段 3 把旋转输入抽象成接口（如 `IRotateInput`），三个实现：
  - PC：滚轮 + R 键（原文档已有）
  - 移动端默认：屏幕角落旋转按钮（≥44px 触点，拖拽中可及，且不被拖拽中的灵石挡住判定）
  - 移动端可选：双指扭转手势（设置项开关）——拖拽中 `TouchCount ≥ 2`，以第一指位置为圆心累计第二指方位角增量，每累计 ~45° 触发一次 90° 旋转（带死区防抖）
- 单手逻辑成立：扭转可单手完成（食指拖拽 + 拇指/中指划弧），按钮通常需另一只手——两方案覆盖不同握持姿势，互补。
- **抽象层阶段 3 就位，扭转手势本体排到阶段 6 打磨。**
- ESC 暂停在移动端不存在：HUD 需加暂停按钮（补进 UIManager）。

### 2.2 屏幕方向：全平台横屏先行，移动端细节推迟

- **定稿**：横屏一套布局通吃（微信/抖音 `game.json` 配 `deviceOrientation: "landscape"`，横屏拼图品类成熟，不奇怪）。
- **三件事必须现在做对**（成本极低，阶段 6 返工很痛）：
  1. 相机按高度适配：`orthographicSize` 由屏幕高度推算；网格 origin 用 `ViewportToWorldPoint` 算；**任何地方不许硬编码世界坐标**（"背篓左下1/4"全部转视口比例）。
  2. Canvas Scaler 一次配好：Scale With Screen Size，参考分辨率 1920×1080。
  3. 输入抽象（见 2.1）。
- 可推迟到阶段 6 / 发布前：扭转手势、性能档位、包体压缩、TMP 中文字体裁剪。

### 2.3 包体与字体（发布前必办）

- 微信小游戏首包建议 ≤4MB、总包有上限：资源压缩 + 必要时分包。
- UI 用 TextMeshProUGUI 显示中文：TMP 的 SDF 中文字体图集很大，必须做常用字裁剪（环境内有 TMPChineseFont 技能可处理）。
- 引擎选型确认：团结引擎 1.8.4 官方支持微信/抖音小游戏导出（WebGL 转换），Rigidbody2D / UI / TMP 均在兼容范围内。

### 2.4 发布侧成本与合规（与开发并行启动）

- Steam：Steam Direct **每款游戏 $100** 注册费（游戏免费 ≠ 上架免费）。
- TapTap / 国内安卓渠道：一般需要**软件著作权**（自申请免费，周期 1-3 个月）。
- 微信 / 抖音小游戏：个人主体可注册，需 **ICP 备案**（免费，有周期）。
- 发布前整理所有 AI 生成 / 素材库素材的授权清单。

## 三、P2 实现层注意事项（编码到对应阶段时对照）

1. **`Update(dt)` 命名冲突**：MonoBehaviour 的魔法方法 `Update()` 不会自动调带参版本。所有管理器统一改名 `Tick(dt)`，由 GameManager 的 Update 集中驱动（`if (IsPlaying()) { qi.Tick(dt); grid.Tick(dt); pot.Tick(dt); }`）。
2. **暂停方案**：`Time.timeScale = 0` + 集中驱动双保险。timeScale=0 自动冻结物理/动画/协程（dt 累加器自然停），暂停面板动画用 unscaled 时间。不要各系统分散检查 IsPaused。
3. **状态 × 物理表**（原文档缺失，补）：
   - InBasket / Cooked 在容器内：Rigidbody2D Dynamic（参与堆积）
   - Cooking：Dynamic
   - 拖拽中：Kinematic（且移到拖拽层，避免放大时挤飞周围堆积块）
   - Placed：Kinematic 或 simulated=false（吸附在格子里，绝不受重力）
   - 暂存：Kinematic 悬空半透明（松手失败后绝不能掉出屏幕）
4. **ShapeEntry 是 struct 却含 `List<Vector2Int>`** —— C# 陷阱：struct 拷贝共享同一个 List，改一个动两个。改成 class。
5. `GetPlacedCells()` / `GetCells()` 等返回内部 List 引用 → 返回副本或 `IReadOnlyList`。
6. **GC**：拖拽预览每帧 `GetMatchedCells` new List → 复用缓冲 List（`Clear()` 后用）。WebGL 小游戏对 GC 卡顿敏感。
7. **可复现性**：LevelConfig 加 `seed`（0 = 随机，非 0 = 确定性），测试模式用固定 seed。
8. **堆叠点选**：物理堆里 OverlapPoint 会命中多块 → 按渲染层/z 排序取最上层那块。
9. **UI 穿透**：拖拽判定前先 `EventSystem.IsPointerOverGameObject` 过滤。
10. **接口衔接**：`GenerateInitialInventory(levelConfig)` 拿不到洞的形状集合 → 改为 `(levelConfig, gridManager)` 或 GenerateLevel 返回"洞→形状列表"。开局生成洞数量未定义 → 定为 `min(holeCount, totalHoles)`。
11. 多块暂存同时回背篓时错开落点（横向偏移 index×0.5 格），避免恢复物理瞬间重叠炸开。
12. 背篓物理堆溢出风险：`SpawnAtBasketTop` 用射线找堆顶；阶段 2 验证点加"50 块压力测试"，堆溢出再切收纳格方案。

## 七、多语言支持：简中 / 繁中 / 英语（2026-10-19 新增需求）

### 决策一览

| 项 | 定案 |
|---|---|
| 需求 | 游戏内可切换 简体中文 / 繁體中文 / English |
| 实现时机 | **接口与表结构现在定稿；实装在阶段 4**（UIManager 出现时）。理由：此前无玩家可见文本，而 UIManager 一旦写死字符串，回头全量改 key 成本高 |
| 技术方案 | **自研轻量 L10n，不用 Unity 官方 Localization 包**。理由：本作文案量小（预计 <200 条 key），官方包重、学习成本高、小游戏导出还要额外验证；自研 = 一个静态类 + 一张表 + 一个切换事件 |
| 繁中策略 | **独立翻译表，不做简→繁自动转换**。神话题材两岸用词有差异，文案量小手写更稳；翻译可由 AI 代劳后人工过一遍 |
| 默认语言 | 首次启动按 `Application.systemLanguage` 检测（zh-CN→简中，zh-TW/zh-HK→繁中，其他→英语）；玩家手动切换后写 PlayerPrefs，优先于系统检测 |
| 美术红线 | 所有美术提示词已注明"无文字"，图内不烘焙文字，切语言不换图（已在《美术资源提示词》落实） |

### 接口形态（阶段 4 按此实现）

```csharp
public static class L10n
{
    public static void Init(LocalizationDatabase db);          // GameManager 启动时
    public static string Get(string key);                      // 取当前语言文案
    public static void SetLanguage(SystemLanguage lang);      // 切换并触发刷新
    public static SystemLanguage GetCurrentLanguage();
    public static event Action OnLanguageChanged;              // UIManager 监听后全量刷新
}
```

数据资产：`LocalizationDatabase : ScriptableObject`（Inspector 可直接编辑），
含 `defaultLanguage` + 每语言一组 `List<StringEntry>(key, value)`，key 用英文蛇形命名
（如 `ui.pause` / `ui.restart` / `level.01.name` / `result.win`）。

### 连带改动

1. **UIManager**（阶段 4）：所有文案走 `L10n.Get(key)`，订阅 `OnLanguageChanged` 全量刷新；设置界面加语言切换（三选项循环或下拉）。
2. **LevelConfig.displayName** → 改存 key（如 `level.01.name`），由 L10n 取显示名。
