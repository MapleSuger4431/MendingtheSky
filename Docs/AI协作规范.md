# 与 AI 协作开发 · 经验清单

> 面向「用 AI 长期协助开发」沉淀的操作规范。每条都来自实际踩坑，不是理论。
> 新增条目请保持同一格式：**标题（日期）** + 做什么 + 为什么 / 怎么做。
> 最后更新：2026-10-29

---

## 一、协作流程（什么时候问、什么时候做）

### 1. 先说明再执行（2026-10-27）

任何修改类操作——改代码 / 场景 / Prefab / 资产、跑会写结果的脚本、git 提交、花额度——先说明「要做什么、改哪些文件、影响什么」，等确认再动手。纯读取不需要确认。

### 2. 反复拷问 + 复述确认（2026-10-27）

开工前用提问把歧义问干净，自己理解清楚后复述一遍需求待确认；执行中遇到不明确处立刻停下；用户没回复就标记入待办，能跳过就跳过，不能跳过先按最优解写上，等用户回来主动确认。

### 3. 先立框架再实现（2026-10-28）

动手写代码前，先交出「目录与文件职责 + 模块边界 + 接口与数据模型 + 扩展点」，框架没定不进入实现。结构乱掉后返工成本远高于先理一遍。

### 4. 布局先行，UI 与逻辑联动（2026-10-28）

玩法定案后先把 UI 骨架摆清楚（坐标 / 尺寸 / 留白）再填细节与美术。布局与逻辑不要割裂：布局会反向决定逻辑实现——例如「灵气条压洞口」最终靠改 `GridManager` 的洞口生成行范围解决，而不是调美术。

### 5. 小步提交，一个主题一个 commit（2026-10-29）

大功能拆成「核心 → 表现 → 配置」多次提交。例：双向旋转拆成「逆时针核心 / 移动端按钮 / 手势+设置」三次。好处是可单独回退、可单独 review、出错时能定位到具体一层。

### 6. 多对话分工（2026-10-27）

设计讨论、执行操作、测试验证各开一个对话，避免单会话上下文互相污染，也避免长对话后期指令漂移。

### 7. 回滚兜底与限时判定（2026-10-27）

凡是「用版本回滚就能解决」的 bug，先设时长阈值，超过就直接回滚验证，不再无限深挖。回滚只针对自己改动的节点，**不要 checkout 整个场景**——会吞掉手工摆位。

> 当前采用阈值：**45 分钟**。超过即回滚到最近可用版本，再在可复现环境里定位根因。

## 二、验证方法（怎么确认真的改对了）

### 8. 三层证据，按成本从低到高（2026-10-29）

| 层级 | 手段 | 耗时 | 适用 |
|---|---|---|---|
| 状态级 | 读 `activeSelf` / `sprite` / 文本内容 / 坐标 | 秒级 | 大多数改动 |
| 行为级 | 调真实入口（`onClick.Invoke()`）走完整调用链 | 分钟级 | 接线是否打通 |
| 视觉级 | 录制 + 人眼或 VLM 判读 | 分钟级 | 最后一道门 |

先用状态级证明，再用行为级证明，最后才看画面。

### 9. 视觉验证是最后一关，不是第一手段（2026-10-29）

能用属性证明的事不要截图。截图也无法证明时间相关的效果——VFX / 动画 / 短时反馈要用多帧录制或慢放。

### 10. 改共享逻辑必跑全套测试（2026-10-29）

每轮改动后跑全部 EditMode 用例（本项目当前 106 条），新增分支补对应用例。测试失败不许提交。

## 三、排查方法（怎么找根因）

### 11. 先量化，再下结论（2026-10-29）

手感 / 数值类判断一律先跑统计。

实例：判断「5 格块是不是太多」→ 实测占全部块 **68.7%**；提出「把上限提到 12」→ 实测 30 格洞从稳定 8 块**退化**到 8.68 块并冒出单格碎块。直觉可以提假设，结论必须由数据支撑。

### 12. 单次采样不可信，时间相关的东西必须多次采样（2026-10-29）

音频输出、动画、粒子、网络请求——单帧读数经常是 0。音频排查时单次 `GetOutputData` 全零，循环采样 12 帧后得到峰值 0.18 / 0.44，差一点误判成引擎哑了。

### 13. 确认「实际生效的那个字段」，不要相信名字（2026-10-29）

| 你以为 | 实际生效 |
|---|---|
| `Image.sprite`（SpriteSwap 切换状态时） | `Image.overrideSprite` |
| `Image.color`（ColorTint 改变状态时） | `CanvasRenderer.SetColor` |

名字像但实际不是的坑，先用最小实验证一遍再下判断。

### 14. 区分环境问题与代码问题（2026-10-29）

Gradle 依赖超时、Mono 后端不支持 Android ARM64、Windows 无法导出 iOS——这些都不该去改代码。报错先问「这是网络 / 工具链 / 平台限制吗」，再问「这是我们自己的 bug 吗」。

### 15. 美术类问题先量像素，不要用坐标推断（2026-10-28）

面板越界、按钮压边、图标贴金边，根因常常是贴图的透明留白，而不是 RectTransform 算错。量 alpha 边界比读数值可靠。

### 16. 最小对照实验定位（2026-10-28）

开 / 关某个子物体各测一次、只改一个变量跑一次，比读代码推理快得多。

## 四、交付与沉淀

### 17. 提交信息写「为什么」，不写「做了什么」（2026-10-29）

代码本身说明做了什么，提交信息要解释动机与取舍。例：「滚轮刻意不分方向——否则上滚在键盘和滚轮两条路径里含义相反」。

### 18. 踩坑写成「根因 + 判据 + 修法」三件套（2026-10-29）

下次遇到同类现象能直接命中，而不是重新推一遍。

### 19. 不可逆操作加二次确认（2026-10-29）

退出游戏、覆盖文件、删除资源——先弹确认或先备份。

### 20. 长任务不要卡住主线程（2026-10-29）

打包、跑测试、批量生成用异步或轮询，并设定超时与失败后的恢复路径。

## 五、一句话版本

> **问清楚再动手，框架定了再写码，布局摆好再填细节；改完先用属性证明，再用行为证明，最后才看画面；拿不准就量化，量化不出就做最小对照；环境问题别当代码 bug 修；每步小提交，每个坑记三件套。**
